# DSOC

This folder defines the contribution standard for the VoiceyBill workspace during the DSOC program.

Program link: https://www.devweekends.com/dsoc/

## Quick Rules

- Open issues with the repository issue forms only.
- Use the correct template for bug reports, feature requests, and questions.
- Attach screenshots or a short video or screen recording for anything visible, interactive, or hard to explain with text alone.
- Open pull requests with the repository PR template and complete every required section before review.
- Include setup evidence and validation output whenever you document setup, onboarding, or reproduction steps.
- Review the feature ideas in [ideas.md](ideas.md) before proposing new work.

## How To Open An Issue

1. Choose the correct repository first.
2. Select the matching issue type:
   - Bug report
   - Feature request
   - Question
3. Write a clear summary of the problem or idea.
4. Describe the expected result, the actual result, and the exact steps to reproduce.
5. Add the environment details that matter, such as OS, browser, device, app version, simulator, or API endpoint.
6. Attach a screenshot, GIF, or short video when the issue affects the UI, a setup step, or any visible flow.
7. Link the related issue if the report is a follow-up or will later become a pull request.

## Issue Template Rules

- Use the matching issue template every time.
- Do not submit blank issues or open-ended issues when a template exists.
- Keep one issue focused on one problem so maintainers can triage it quickly.
- Include reproduction steps that another contributor can follow without guessing.
- Include screenshots, screen recordings, or videos for visual bugs, setup failures, and feature ideas that need context.

## Pull Request Rules

- Use the repository PR template for every pull request.
- Complete every required section before requesting review.
- Explain what changed, why it changed, and how it was validated.
- Link the issue, discussion, or feature request that motivated the change.
- Attach screenshots or a short video or screen recording for UI changes, setup changes, and any other visible behavior.
- Keep each PR small and focused so it is easy to review and merge.

## Media Policy

The program expects proof for anything that is visible or hard to verify from text alone.

- UI changes require screenshots or a screen recording.
- Setup guides require screenshots or a short recording whenever a step produces visible output.
- Bug reports require screenshots or recordings when the issue is visible.
- Feature requests require a screenshot, mockup, GIF, or video when the idea affects a user-facing flow.

## Setup And Documentation Standards

- Document the exact commands you ran.
- Include the output that proves success.
- Include the media that proves the visible step worked.
- Mention machine-specific notes when they affect setup, such as OS, simulator, device, or Docker configuration.
- Update the setup guide whenever the workflow changes.

## Contributor Checklist

- Correct issue template used
- Screenshot, GIF, or video attached when relevant
- PR template fully completed
- Validation output included
- Setup steps documented clearly
- Related issue linked
- Feature idea reviewed in [ideas.md](ideas.md) when applicable
